# Comparing libraries

This page sets Geode next to four other Roblox DataStore libraries: ProfileStore, ProfileService, Lapis and DataStore2. It lists what each one does and how, taken from their source code at the versions below. It doesn't rank them. Measured numbers are on [Benchmarks](benchmarks), and moving data across is covered in [Coming from ProfileStore, ProfileService or Lapis](coming-from-profilestore).

## Details

### Geode

A profile is one DataStore key holding the data and its bookkeeping. The lease, the data and the purchase ids are written together by one UpdateAsync, so a server whose lease was taken can't write anymore. Loads that find a live holder ask it to release over MessagingService, and a short lived MemoryStore key repeats the answer in case a message is lost. Neither is needed for correctness. See [How it works](how-it-works) for the full path.

### ProfileStore

The session is `MetaData.ActiveSession = {PlaceId, JobId, session id}` inside the saved record. A server that finds another session writes `ForceLoadSession`, sends `EndSession` to the holder on the MessagingService topic `PS_<session id>`, reads again after `FIRST_LOAD_REPEAT` (5 s) and then every `LOAD_REPEAT_PERIOD` (10 s), and takes the session once `SESSION_STEAL` (40 s) has passed. The holder saves and ends its session when the message arrives, and also when one of its saves sees a pending `ForceLoadSession`. Autosave runs every `AUTO_SAVE_PERIOD` (300 s). `StartSessionAsync` gives up after `START_SESSION_TIMEOUT` (120 s) of failed requests. In Studio it first writes to a DataStore named `____PS` to find out whether API access is on, and runs on an in-memory store when it isn't. It's on Wally as `lm-loleris/profilestore`, latest 1.0.3 when this page was written.

### ProfileService

The session is `MetaData.ActiveSession = {PlaceId, JobId}`. `LoadProfileAsync(key, handler)` calls the handler when the profile is held, and the handler answers `"Repeat"`, `"Cancel"`, `"ForceLoad"` or `"Steal"`. With `"ForceLoad"` the loading server writes `ForceLoadSession` and the holder releases when one of its autosaves (spread over `AutoSaveProfiles`, 30 s) sees it. After `ForceLoadMaxSteps` (8) tries the loading server takes the session. Every DataStore call for one key waits `RobloxWriteCooldown` (7 s) after the previous one, so the 8 tries take roughly a minute when the holder never answers. TODO(verify) that time, the bench didn't measure a holder that never answers. In the [benchmarks](benchmarks) a holder that kept the profile let go after about 21 s, on its next autosave. It doesn't use MessagingService. The README asks new projects to use ProfileStore.

### Lapis

The lock is a `lockId` stored with the data. A load that finds a lock younger than `LOCK_EXPIRE` (30 minutes, measured from the key's last update) retries `loadAttempts` (20) times, `loadRetryDelay` (1 s) apart, then fails with "Could not acquire lock". There's no option to take a held lock. Every request waits until the request budget for its type is above zero, so Lapis queues instead of going over the budget. Pending saves and closes for one key are combined into one request. Data is deep frozen by default and replaced with `document:write`. Its README warns that it hasn't been used in a large production game yet.

### DataStore2

There's no session lock, so two servers can hold and save the same player's data at once. Data is cached per player and saved when the player leaves, on `game:BindToClose` and on `:Save()`. The default saving method, OrderedBackups, writes every save to a new key and keeps an OrderedDataStore pointing at the latest one, so old saves stay readable. The Standard method uses one key per player. In Studio it doesn't save unless a `SaveInStudio` BoolValue in ServerStorage is set. `Combine` stores several named values under one key.

Its license allows copying and changing the code. When a published game uses a changed copy, the changes have to be published too, for example as a fork on GitHub.
